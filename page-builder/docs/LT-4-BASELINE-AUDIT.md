# LT-4 — Baseline & Structural Correspondence: Audit & Architecture

**Status: AUDIT + DESIGN (LT-4 kickoff). Analysis only — no schema, no code, no service change yet.**
Two consequential decisions are surfaced below and must be confirmed before implementation.

LT-4 establishes the **first authoritative provenance model** (per
[`LT-3-FINAL-GOVERNANCE.md`](./LT-3-FINAL-GOVERNANCE.md) Invariant 1): stable cross-locale node
correspondence + an immutable source baseline, so future diff (LT-5) and synchronization (LT-6) are
possible **without** locking layouts together. No diff, sync, plan, merge, or execution in LT-4.

---

## 1. Audit findings

- **Binding table** (`pb_layout_translation_bindings`) has **no** baseline/correspondence column — only
  the identity keys, `layout_id`, `locale`, and the three state dimensions.
- **LT-3 clone is verbatim**: it stamps no correspondence and records no baseline. Consequently a
  cloned target currently shares **identical node ids** with its source (natural, implicit
  correspondence), but nothing is persisted or formalized.
- **Baseline primitive exists** (frozen): `DesignFingerprint::of(payload)` =
  `sha256(DesignPackageManifest::canonicalJson(payload))` — content-addressed, order-independent.
- **Frozen guidance:** LT-0-ADR-001 **D6** (node correspondence lives in each node's `data` bag — the
  normalizer strips unknown top-level node keys but preserves `data`) and **D7** (baseline is a
  content-addressed fingerprint over an **id-free and correspondence-free** canonical form, plugin-owned;
  Core `cms.revision` is rejected as the baseline store because it prunes).

---

## 2. Structural correspondence design (per D6)

Each node carries a stable cross-locale correspondence id in `data` (e.g. `data['_origin']`), so a
source node and its target counterpart map to each other even after independent target edits or
physical-id regeneration. Two identities, exactly as LT-0 defined:

- **physical `id`** — document-local (may be regenerated by editor operations);
- **origin correspondence** — stable across locale layouts, in `data`.

**Target-owned nodes** (added only to the target) carry a null/own correspondence marker and are never
overwritten or removed by future source synchronization.

### ⛔ Decision A — how correspondence is established for existing/verbatim clones

Because LT-3 copied verbatim, source and target share identical physical node ids today. Options:

| Option | Approach | Note |
|---|---|---|
| **A1 (recommended)** | LT-4 *stamps* an explicit `data['_origin']` on both source and target derived from the node's current id at baseline time; thereafter correspondence is the stamped origin, independent of physical id. | Robust to future id regeneration; additive to `data` (survives the normalizer). Requires a one-time correspondence-stamping pass over source + target. |
| A2 | Treat the preserved physical id as the correspondence (no stamping). | Zero writes, but fragile — any future id regeneration (duplicate/import paths already regenerate ids) breaks correspondence. |

Recommendation: **A1** (explicit, stable, additive), applied read-through/at-baseline, never mutating the source document's meaning (only adding correspondence metadata).

---

## 3. Baseline design (per D7)

A **baseline** is an immutable reference to the source's state at the last successful correspondence/sync
point: a content-addressed **fingerprint** (`DesignFingerprint`-style, computed over the canonical form
with physical ids **and** correspondence metadata stripped, so source and target hash comparably) plus a
reference to the source `pb_layouts.id` and a captured-at marker. `IN_SYNC` (set by LT-3) is *not* the
baseline; LT-4 records the authoritative baseline explicitly.

### ⛔ Decision B — where the baseline is persisted

| Option | Approach | Verdict |
|---|---|---|
| **B1 (recommended)** | **Additive columns on the binding**: `baseline_fingerprint` (nullable string), `baseline_source_layout_id` (nullable FK/int), `baseline_captured_at` (nullable timestamp). One baseline per target binding; nullable so existing bindings and single-language behaviour are unchanged. | Smallest surface; the binding already owns per-translation status; additive migration; reversible. |
| B2 | New `pb_layout_translation_baselines` table keyed by `page_translation_key` (1:1 with binding). | Cleaner isolation; more plumbing; another table. |

Recommendation: **B1** (additive nullable columns on the existing binding) — one baseline per target, congruent with the binding's per-translation ownership. Either way it is a **new migration** (surfaced here per the LT-3/§25 discipline — no schema is written until confirmed, and the LT-2/LT-3 migrations are never modified).

---

## 4. Diagnostics & integrity (LT-4 scope)

Read-only, never-repairing: report baseline presence/absence, fingerprint, correspondence coverage, and
**orphaned/ambiguous correspondence** (a target node whose origin has no source counterpart, or duplicate
origins). Extends the existing never-throwing diagnostics convention; no auto-repair.

## 5. Non-goals (LT-4)

No structural diff (LT-5), no synchronization plan/execution/merge/conflict resolution (LT-6/7), no UI
(LT-8), no baseline-driven auto-tracking of source changes, no Core change, no frozen LT-1/LT-2/LT-3
contract change.

## 6. Proposed LT-4 phase plan (on confirmation)

1. **LT-4a** Correspondence foundation — an additive correspondence-metadata model in `data` + a
   read-only correspondence reader/validator (Decision A1). No schema.
2. **LT-4b** Baseline persistence — additive migration (Decision B1) + a plugin-owned baseline
   writer/reader returning domain contracts, recorded at clone/first-baseline. New migration (created,
   not executed).
3. **LT-4c** Diagnostics + integrity + architecture-regression + tests.
